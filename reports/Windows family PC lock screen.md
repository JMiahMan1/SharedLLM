# Lock the session, not the screen

The evidence converges on one design: a **signed, visible SYSTEM service whose hard enforcement is session-level — WTS logoff at budget/window exhaustion plus a re-logon rear-guard — with the fullscreen overlay demoted to a courtesy screen**, a **DNS-backbone + browser-policy web filter pinned against DoH** and rolled out report-only → enforce, **net10.0 self-contained** single-file builds signed via **Azure Artifact Signing** (or loudly unsigned), and **MIT/Apache-2.0 code and patterns mined from four OSS projects** (vigil, robertpin/WindowsParentalControl, whip4brats, SecureAppLocker) — while **rejecting SDDL/SafeBoot tricks outright**. Windows Home is the baseline; every strong native lever (Assigned Access, AppLocker enforcement, kiosk) is Pro/Enterprise-only and must ship as opt-in extras, never as the enforcement story. The honest residual risks — admin child account, safe mode, USB/other-OS boot — are acknowledged in the risk table, not solved. This sharpens the plan in `docs/WINDOWS_LOCK_SCREEN.md` in five concrete ways: net8 → net10, "overlay is the lock" → "session is the lock", a real DNS recommendation with DoH pinning, a real signing/CI decision, and an explicit per-detection risk matrix.

## OSS prior art: borrow the architecture, never the license-violating code

The Windows-native parental-control OSS space is niche, hobbyist-grade, or brand-new, and nothing approaches Qustodio or Family Safety maturity — but four projects are directly mineable, and their licenses dictate what may be copied. **[deresterr/vigil](https://github.com/deresterr/vigil)** (MIT, 0★, created Nov 2026) is the closest architectural match to the target design: a Docker/FastAPI server decides lock state, a Windows service runs a fail-closed fullscreen lock covering all monitors that blocks Win/Alt+Tab/Alt+F4, server silence for 30 s means locked, unlock works offline via TOTP, and a 5-minute "guardian" re-applies service/file state — with an honest threat model admitting an administrator child *can* defeat it and receives alerts, not guarantees ([README](https://github.com/deresterr/vigil/blob/main/README.md)). Treat it as alpha and steal the *shape* (fail-closed arbitration, guardian re-assert loop, TOTP-on-lock offline unlock, MIT permitting adaptation), not its HTTP-not-TLS pairing. **geogengames-hue/MonitorAndControl** is the feature-richest reference — per-app/account daily limits SID-keyed, shared app groups, schedules, bedtime that *signs the account out*, an ask-parent ntfy/Telegram flow with single-use decline links that grant nothing and expire in 12 h, and site blocking implemented as browser Windows policies (`URLBlocklist` Chrome/Edge/Brave, `WebsiteFilter` Firefox) written by the SYSTEM service — but its GitHub license is NOASSERTION/custom, so read it for UX and policy plumbing only, never code ([README](https://github.com/geogengames-hue/MonitorAndControl/blob/main/README.md)). **[robertpin/WindowsParentalControl](https://github.com/robertpin/WindowsParentalControl)** (MIT, .NET 8, 2★, self-admittedly "vibe-coded") is the installer and session-management template: `sc.exe failure … actions= restart/10000/30000/restart/60000` in the Inno script, a `WindowsServiceLifetime` subclass overriding `CanHandleSessionChangeEvent`/`CanHandlePowerEvent`, WTS P/Invoke (`WTSEnumerateSessionsW`, `WTSQuerySessionInformationW`, `WTSLogoffSession`) for per-session time accounting and clock-tamper hints ([Program.cs](https://raw.githubusercontent.com/robertpin/WindowsParentalControl/main/src/ParentalControl.Service/Program.cs), [ParentalControl.iss](https://raw.githubusercontent.com/robertpin/WindowsParentalControl/main/installer/ParentalControl.iss)). **[whip4brats](https://github.com/rozensoftware/whip4brats)** (Apache-2.0/MIT) demonstrates the mandatory Session-0 → user-session topology: SYSTEM service → TCP command server (`executor`) → shared memory → `BratLocker` (C++20, `WS_POPUP` + topmost re-asserted on a 3 s `WM_TIMER`, mutex single-instance, password-grants-time dialog) ([BratLocker.cpp](https://raw.githubusercontent.com/rozensoftware/whip4brats/master/BratLocker/BratLocker/BratLocker.cpp)). **[SecureAppLocker](https://github.com/osmanonurkoc/SecureAppLocker)** (MIT) is the anti-tamper drop-in: `EnforceSecurityACLs()` re-applies SYSTEM+Administrators-only `SetAccessRuleProtection` on `%ProgramData%` every service start, and its Session-0 named-pipe server uses `PipeSecurity` denying NetworkSid and allowing Interactive+LocalSystem — copy both routines nearly verbatim ([ConfigManager.cs](https://raw.githubusercontent.com/osmanonurkoc/SecureAppLocker/main/SecureAppLocker.Core/ConfigManager.cs)). For foreground tracking, reuse **[ActivityWatch's aw-watcher-window](https://github.com/ActivityWatch/aw-watcher-window)** (MPL-2.0) `windows.py` logic — `GetForegroundWindow` → `GetWindowThreadProcessId` → `GetModuleFileNameEx`, with the ApplicationFrameHost child-window walk for UWP apps — in C# ([source](https://raw.githubusercontent.com/ActivityWatch/aw-watcher-window/master/aw_watcher_window/windows.py)); file-level copyleft is fine for a private hub but keep it as a library/reference, not embedded code. The rule engine itself should be **reimplemented**, not lifted: [screenguard](https://github.com/adambie/screenguard) (AGPL-3.0) and [ScreenTimeTracker](https://github.com/majianchuan/screen-time-tracker) (GPL-3.0) are share-alike traps if the hub is ever published — reimplement the ~200-line model (day-of-week → limit/window/weekend/bonus with monotonic clock and midnight rollover) guided by MIT exemplars (vigil, Focusd, [HAFamilyLink](https://github.com/noiwid/HAFamilyLink)). For the update pipeline, mirror Rust's [self_update](https://github.com/jaemk/self_update) (MIT): checksum → signed digest → signature verify → `verify_archive`/`verify_binary` hooks → transactional `MoveAll` swap with rename-away of the running exe and rollback on failure. License bottom line: **copy MIT/Apache-2.0 with notices retained; re-implement GPL/AGPL; treat everything else (MonitorAndControl, K9/BlockerFlow, Clarivue-AI, FamillyKJ) as reference-reading only** — and stay far away from the cracked/SEO "parental control" repos polluting GitHub topics.

## Enforce the session, not the pixels: the lock design for Home and Pro

The single strongest platform finding is that **Windows has no device-owner or owner-key model** — ChromeOS generates an owner key pair at first boot, signs device policy with it, and requires factory reset to shed enterprise control ([Chromium ownership](https://chromium.googlesource.com/chromium/src/+/46fa99d0f2b3c1a940c25e4849a3fbeff2be0a6a/components/ownership), [enrollment](https://chromium.googlesource.com/chromium/src/+/fde062ce944c6238d9217cfd2109242f1ffad73f/docs/enterprise/enrollment.md)) — and Microsoft Family Safety, the only native consumer analog, is **account-bound, not device-bound**: a real Microsoft child account, Edge for web filtering, server-synced policy ([Family Safety screen-time docs](https://support.microsoft.com/en-us/family-safety/set-screen-time-limits-across-devices)). That account binding is exactly why Family Safety fails in the field: local accounts get no features and no warning; flipping to an admin account self-disarms it; a **mass Chrome block landed in June 2025** precisely because the only native stop for non-Edge browsers is **App and game time limits** — coarse per-app blocking used *as a substitute for account-bound web filtering* — and was bypassed by renaming `chrome.exe` to `chrome1.exe` ([Windows Central](https://www.windowscentral.com/software-apps/browsing/microsoft-is-blocking-google-chrome-in-the-name-of-family-safety-but-this-time-it-actually-makes-sense), [How-To Geek](https://www.howtogeek.com/microsoft-family-safety-feature-is-blocking-chrome-on-windows), [Family Safety filter docs](https://support.microsoft.com/en-us/family-safety/filter-websites-and-searches-using-microsoft-family-safety)); in **December 2025 filtering silently stopped** for days across Edge due to a server-side policy-sync failure, with Microsoft support rejecting escalation ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5667309/microsoft-family-safety-filtering-is-not-working-f)); and `WpcMonSvc` simply stops, killing app limits and reporting with no UI warning ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/3864263/my-son-is-bypassing-family-safety-limits)). The design lesson cuts two ways and the plan must internalize both: **enforce at machine/session level, never at account level** — and **never rely on exe-name matching as a primary control either**, because name-based "app limits" are provably bypassable; they are an acceptable *coarse backstop* underneath session enforcement and browser policies, not the enforcement itself.

Every real OSS project ships the same enforcement shape, and the plan currently under-weights it: **enforce by session, not by pixel**. MonitorAndControl signs the child's account out at bedtime/limit exhaustion; WindowsParentalControl does the same via `WTSLogoffSession`; the topmost-overlay everyone builds has a trail of failure modes (Stretchly's issue tracker — [#639](https://github.com/hovancik/stretchly/issues/639), [#524](https://github.com/hovancik/stretchly/issues/524), [#355](https://github.com/hovancik/stretchly/issues/355) — catalogs overlay-vs-exclusive-fullscreen and dual-monitor breakage); `LockWorkstation` is useless because the child knows their own password. The recommended design, identical on **Home and Pro** (Home is the baseline): the SYSTEM service watches the child's session via WTS; at window/budget exhaustion it shows a courtesy overlay counting down **15/5/1 minutes** (Norton's cadence, [Norton support](https://support.norton.com/sp/en/us/norton-snap/1.0/solutions/v127151815)), then calls `WTSLogoffSession` — and if a child session starts during a bedtime/school window, a session-start rear-guard in the service triggers an immediate logoff after flashing a "Not yet — bedtime" overlay. The overlay itself is one **borderless topmost WS_POPUP form per monitor** (`Screen.AllScreens`), `PerMonitorV2` DPI awareness, `WS_EX_TOPMOST|WS_EX_TOOLWINDOW`, re-asserting `HWND_TOPMOST` via a BratLocker-style timer or `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`, `Deactivate` → re-`Activate()` — a courtesy surface, never the security boundary, and unachievable against exclusive-fullscreen games (enforce those at logon granularity). Sleep-policy failures fail **closed** (locked/logoff); app-block and overlay failures fail **open** (a wedged overlay must never brick the PC). Overlay-as-lock stays in the plan only as the pre-logoff courtesy and re-logon signage; the plan's "Device owner ❌ impossible" row stays, but the honest replacement is logoff + rear-guard, not a stronger window.

**Assigned Access is Pro/Education/Enterprise/IoT-only and must not anchor enforcement** ([Assigned Access overview](https://learn.microsoft.com/en-us/windows/configuration/assigned-access/overview)). It offers kiosk single-app mode (UWP/AUMID, fullscreen above lock screen, **no multi-monitor support**) and multi-app restricted user experience (allowed-app list + tailored Start/Taskbar + AppLocker SRP at the `SrpV2` layer), applied per-user via GPO/CSP/WMI bridge or `Set-AssignedAccess`, with sign-out required to switch modes, console-only sign-in, no RDP, and removed configs leaving Start-menu residue ([single-app kiosk](https://learn.microsoft.com/en-us/windows/configuration/assigned-access/configure-single-app-kiosk), [multi-app kiosk](https://learn.microsoft.com/en-us/windows/configuration/assigned-access/configure-multi-app-kiosk?tabs=ps)). No commercial suite or OSS project ships it for family PCs — the edition gate kills the consumer TAM. Ship it as a **Pro-only opt-in "school hours" mode** (multi-app allowlist, Edge-school-sites + Word + homework app, applied by a time-of-day config-swapper in P5), explicitly labeled Pro/Edu-only in capabilities reporting. Shell Launcher (custom kids shell) is Enterprise/Education-only and out of scope. AppLocker's SRP enforcement is likewise Pro+ — on Home, registry-authored SRP policy keys exist but are not enforced by the OS; treat as advisory there. **Browser policies are the one Pro-strength lever that works on Home**: `HKLM\SOFTWARE\Policies\Microsoft\Edge\URLBlocklist` / `HKLM\SOFTWARE\Policies\Google\Chrome\URLBlocklist` (REG_SZ list, ≤1000 entries, `URLAllowlist` wins, `*` blocks all), `ForceGoogleSafeSearch=true` / `ForceBingSafeSearch=2` (**0 = no restrictions, Moderate does not filter text** — the single most surprising gap), `ForceYouTubeRestrict`, and Firefox `policies.json` `WebsiteFilter` — all keys, not gpedit, so they deploy on Home but require admin to change ([Edge URLBlocklist](https://learn.microsoft.com/en-us/deployEdge/microsoft-edge-policies/urlblocklist), [ForceBingSafeSearch](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/forcebingsafesearch), [Chrome enterprise help](https://support.google.com/chrome/a/answer/7532419), [Firefox WebsiteFilter](https://firefox-admin-docs.mozilla.org/reference/policies/websitefilter)). Ship these machine-wide **plus** HKCU per-child-scoped variants, with an on-device self-check (agent reads `edge://policy`/`chrome://policy` state and reports "policy live: yes/no") — visibility nobody else ships.

## DNS plus DoH-pinning: the web filter that survives 2026 browsers

**Recommendation: AdGuard Home (primary) or Technitium (if you want DHCP/clustering/self-hosted DoT-DoH) installed on the child PC itself as a Windows service, adapter DNS pinned to 127.0.0.1, with browser DoH pinned off by policy, blocklists = low-false-positive base + category lists + HaGeZi DoH-bypass, rolled out report-only → enforce over ~2–3 weeks. The policy-keys approach is the mandatory browser-layer complement, not a DNS substitute.** [AdGuard Home](https://github.com/AdguardTeam/AdGuardHome) (GPL-3.0, ~38.3k★, very active, native Windows service, per-client rules/blocked-services-with-schedules, query log with 6h–90d rotation — effective retention ≈2× the rotation interval, confirmed by the maintainer ([issue #7893](https://github.com/AdguardTeam/AdGuardHome/issues/7893)) — `anonymize_client_ip`, `ignored: [*.arpa]`) is the default: lowest fuss, best UI, domain-only logging. [Technitium DNS Server](https://github.com/TechnitiumSoftware/DnsServer) (GPL-3.0, ~10.3k★, C#/.NET, native Windows service + MSI, built-in DHCP, Advanced Blocking per-client regex, sinkhole-CNAME detection, hosted DoT/DoH) is the pick if you want the same box serving the LAN or self-hosted encrypted DNS; it **cannot** do per-app filtering or report-only either — use HaGeZi `*-onlydomains.txt` lists with it ([Technitium](https://github.com/TechnitiumSoftware/DnsServer), [blocklist formats](https://github.com/hagezi/dns-blocklists)). Skip CoreDNS (hand-rolled, no UI), Acrylic (hobby-grade, no per-client), Pi-hole (not Windows-native), OpenDNS FamilyShield (free tier alive but sunset-risk inside Cisco's Umbrella SIG/DNS EOL announced 2026-09-01 — do not build new dependency on it, [EOL15975](https://www.cisco.com/c/en/us/products/collateral/security/security-cloud/umbrella-sig-dns-eol.html)), and CleanBrowsing (free tier is blunt; granular category policy paywalled; not OSS).

**DoH pinning is non-optional.** Chrome ships "Use secure DNS" **on by default** (auto-upgrade to DoH when the resolver supports it, ignoring OS DoH in its internal resolver), and Edge defaults to Automatic secure DNS backed by Windows 11's DoH-capable stack — so in 2026 all three major engines encrypt DNS by default, silently defeating any IP/port-53 filter ([Google blog](https://blog.google/products-and-platforms/products/chrome/more-intuitive-privacy-and-security-controls-chrome/), [Edge DnsOverHttpsMode](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/dnsoverhttpsmode), [Barracuda](https://documentation.campus.barracuda.com/wiki/spaces/BCGA/pages/1769628/How+to+Disable+Secure+DNS), [Chromium issue 337445645](https://issues.chromium.org/issues/337445645)). The minimal sufficient set: (1) static per-adapter DNS → 127.0.0.1 on the child PC via `netsh interface ip set dnsservers "Wi-Fi" static 127.0.0.1` (no secondary DNS — Windows races fallback queries and punches a permanent hole past the filter); (2) `HKLM\SOFTWARE\Policies\Microsoft\Edge\DnsOverHttpsMode=off` (REG_SZ) and Chrome equivalent (`HKLM\SOFTWARE\Policies\Google\Chrome\DnsOverHttpsMode=off`), or HKCU-scoped for child-only; (3) Firefox `policies.json` `DNSOverHTTPS: disabled` (Firefox is not covered by Chrome/Edge keys); (4) HaGeZi `doh.txt` (3,568) / `doh-vpn-proxy-bypass.txt` (16,424) in the resolver plus DoH IPs at the firewall; (5) outbound TCP/UDP 853 blocked (per-child-SID scoping works in WFAS, but gpedit is absent on Home — use registry + `netsh advfirewall`, which works on Home; verify exact `user=` SID syntax against [MS Learn](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-advfirewall-firewall) before scripting). The plan's "block outbound 53/853 for all non-proxy traffic" is correct and stays — just add Browser `DoH=off` and the DoH-bypass list, which the plan currently lacks.

**Report-only is a workflow, not a toggle** — neither AGH nor Technitium has a dry-run mode. The rollout: weeks 1–2 run AGH with filtering effectively off (or only oisd small as smoke test), query log at 7-day interval, `anonymize_client_ip` off for per-device attribution, `*.arpa` ignored; weekly export → match eTLD+1 against the ~200-domain category list offline → promote matched domains; watch telemetry noise (google-analytics et al. — prefer HaGeZi PRO over hand-appending analytics). Then enable base list ([oisd small](https://oisd.nl/) or HaGeZi PRO, [lists](https://github.com/hagezi/dns-blocklists)) → whitelist the empirically-discovered 2–5 CDN breakages (Amazon/EA: `cdn.optimizely.com`, `split.io`; Steam/Riot/Epic CDNs must resolve) → then StevenBlack `social`+`gambling` alternates ([StevenBlack/hosts](https://github.com/StevenBlack/hosts)) or HaGeZi Social/Gambling → enforce. Test matrix before locking: Microsoft Store sign-in, Xbox Game Pass, Steam download, Roblox join, Epic login, Discord voice, Twitch playback. **Skip HaGeZi Ultimate, WindowsSpyBlocker spy.txt, Prigent-scale adult lists** — they break Store/Xbox/WhatsApp. Curated ~200-domain list (twitch.tv, discord.gg/canary/ptb, roblox.com, minecraft.net, steampowered.com, epicgames CDNs you do *not* block) has no quality pre-made list — curate by hand; that is the config cost of category filtering, and it is the same trade Kaspersky/Family Safety accept. Device-level beats router-level for a single family PC (survives router swaps, ISP DNS hijack, travel); router/OpenWrt + AGH comes later if the whole household should be covered. Accept the limits honestly: domain-granularity only, chat/streaming blocked wholesale, and DNS never sees QUIC/ECH contents — which is precisely why the DoH-off pinning and per-SID 853 block matter, and why portable user-installed VPNs remain the residual hole requiring app control. Keep domain-only logs (no URLs) — it preserves the agent's no-content-telemetry promise end to end.

## net10, Azure Artifact Signing, and a publish gate that holds

**Ratify net10.0-windows, self-contained single-file, `PublishReadyToRun=true`, trimming disabled, win-x64** — the plan's .NET 8 pin is stale: net8.0's LTS ended November 2026 (i.e., now), .NET 10 is the current LTS, and NativeAOT does not support WinForms while self-contained single-file JIT does ([single-file deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview), [Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), [.NET 10 packaging](https://andrewlock.net/exploring-dotnet-10-preview-features-7-packaging-self-contained-and-native-aot-dotnet-tools-for-nuget/)). Keep one assembly for service + tray host only if you respect Session-0 UI constraints — realistically ship `jarvis-guard.exe` (service) and `jarvis-tray.exe`/`jarvis-lock.exe` (user-session) from one csproj with distinct outputs; pin the SDK in CI rather than trusting IDE publish (VS2026 has produced incorrect single-file output).

**Signing decision: Azure Artifact Signing (renamed from Trusted Signing, ~Jan 2026) Basic at $9.99/month** (pricing from secondary sources; verify on the Azure pricing page) if you are a US/Canada individual with an Azure Individual billing account — otherwise SignPath Foundation (free), else loudly unsigned. Artifact Signing puts your name as publisher, needs no token, and integrates via OIDC (`azure/login@v3` + `id-token: write`, app registration with federated credential `repo:owner/repo:environment:release`) with `azure/artifact-signing-action@v2`; certificates live in FIPS 140-3 HSMs with zero-touch renewal; identity validation takes 1–20 business days, and changing identity details restarts validation and forfeits accumulated SmartScreen reputation — so fix the identity once ([overview](https://learn.microsoft.com/en-us/azure/artifact-signing/overview), [quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart), [action](https://github.com/Azure/artifact-signing-action), [Hanselman walkthrough](https://www.hanselman.com/blog/automatically-signing-a-windows-exe-with-azure-trusted-signing-dotnet-sign-and-github-actions)). **EV is dead for SmartScreen purposes** ("EV certificates no longer bypass SmartScreen"), self-signed is indistinguishable from unsigned, and unsigned-per-file reputation resets to zero on every release — sign everything with one stable cert ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). [SignPath Foundation](https://signpath.org/) is genuinely free for OSI-open projects but publishes under **SignPath Foundation** as publisher, requires manual per-release approval, a public code-signing-policy page naming SignPath + team roles, strict metadata enforcement, and sole discretion — a parental-control tool will likely face scrutiny, so treat it as real but bureaucratic; apply early. Timestamp everything with **`/tr http://timestamp.acs.microsoft.com /td SHA256`** (or `timestamp.digicert.com`); current signtool **rejects HTTPS RFC 3161 URLs**, SHA-384/512 timestamps stopped being honored upstream in May 2025 ([gist fd754e](https://gist.github.com/Manouchehri/fd754e402d98430243455713efada710)), and a build that signed but failed to timestamp **must fail**, not ship ([Microsoft Q&A 6033027](https://learn.microsoft.com/en-sg/answers/questions/6033027/signtool-sdk-10-0-26100-0-rejects-rfc-3161-https-u), [DigiCert KB](https://knowledge.digicert.com/solution/troubleshooting-timestamping-problems)). Already-shipped timestamped files stay valid after cert expiry; never mix legacy `/t` with RFC 3161. Watch for "PUA" heuristic false positives on parental-control binaries and file early at Microsoft Security Intelligence (wdsi/filesubmission).

**CI shape**: `windows-latest` (= Windows Server 2025; VS2026 default migration began June 2026, [runner-images](https://github.com/actions/runner-images)), `actions/setup-dotnet` pinning `dotnet-version`, `dotnet publish -c Release -r win-x64 --self-contained -p:PublishSingleFile=true -p:PublishReadyToRun=true -p:Version=<v>`, sign, then attest with **[`actions/attest-build-provenance`](https://github.com/actions/attest-build-provenance)** and an SBOM via `actions/attest` + `anchore/sbom-action` (needs `id-token: write` + `attestations: write`; free on public repos) so anyone can `gh attestation verify` the exe against the workflow — this is the supply-chain story that makes a family agent verifiably yours; leave the artifact-signing action's dependency cache **off** (poisoning). Keep the plan's publish gate — PRs build + unit-test only (rules-engine fixtures run on Linux too), publish only on `microservices` push with `X-Internal-Secret` and OIDC, endpoint refuses anything else, and add an `environment: release` required-reviewer job as the human gate. Sign the **setup.exe too** (Inno output is a PE), build it with `choco install innosetup` (not preinstalled), install with `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /LOG=`, and ACL the install dir `SYSTEM:(OI)(CI)F` / `Administrators:(OI)(CI)F` / `Users:(OI)(CI)RX` ([Inno cmdline](https://jrsoftware.org/ishelp/topic_setupcmdline.htm)). Ship `version.json` + `SHA256SUMS` to the server, and implement the update loop in-service in self_update's order: fetch manifest → stage in ACL'd ProgramData (never %TEMP%) → SHA-256 → Authenticode via `WinVerifyTrust` → rename running exe to `.old` → copy new → SCM stop/start → health-check (service sets `LastGoodVersion` or answers a pipe ping within N seconds) → on failure rename `.old` back and raise a parent alert. There is **no .NET OSS ready-made for this** — Tauri delegates to installers, AutoUpdater.NET leaves verification to the caller, Squirrel's signature story is weak — so implement the ~150-line ladder yourself and keep the updater as a stable, rarely-updated bootstrap (or at minimum the rename-swap inside the service) to avoid self-bricking. Keep the plan's "MDM push → exe downloads → signature verify → atomic swap → fail closed to old build" semantics, with one addition: a **rollback sentinel** in ACL'd ProgramData that pins `version.json`'s served version after a crash-loop. SmartScreen will nag on first browser download regardless; control the five family PCs via the elevated Inno install (or `Unblock-File`) and the nag never fires — reputation then builds per-cert, so do not churn identity.

## Anti-tamper without the malware playbook — and the honest risk table

**Adopt exactly the composite every respectable OSS project uses, and explicitly reject the two moves the prompt names.** The composite: child = standard user, parent = admin (the single highest-leverage control); service as LocalSystem with SCM recovery set at install (`sc.exe failure … reset= 86400 actions= restart/10000/restart/30000/restart/60000`); `C:\ProgramData\Jarvis Guard` and the install dir ACL'd with .NET `SetAccessControl`/`SetAccessRuleProtection` (SYSTEM+Administrators only, re-asserted on every service start — SecureAppLocker's `EnforceSecurityACLs()` verbatim); desktop/Session-0 IPC over named pipes with the deny-Network/allow-Interactive+SYSTEM `PipeSecurity`; admin UI holding the PBKDF2 parent secret via DPAPI `ProtectLocalData`; named-mutex single-instance; uninstall only through the elevated Inno flow, which stops/deletes service → `sc delete` → reports `guard_missing`. **Do not ship `sc sdset` SDDL deny-stop ACEs** — that pattern exists in the wild only in malware (Glupteba, documented by [Splunk](https://www.splunk.com/en_us/blog/security/windows-security-sddl-guide-access-control.html)), is a hand-maintained string that breaks `sc query` UX, and does nothing against Safe Mode anyway. **Do not touch SafeBoot keys** — no OSS prior art, blocks legitimate servicing, and "don't fight the OS" is the right sanity for a family device. **Reject scheduled-task heartbeats** — redundant with SCM recovery and one more thing to audit; a 1 Hz liveness pulse from the user-session tray (which toasts the parent on service death) is asymmetric in Session 0's favor and sufficient. Fail-secure on crash-loop: if the budget engine itself is repeatedly failing, default to locked/logoff, never granted. If you ever want beyond-OEM whitelisting, remember AppLocker enforcement is Pro+; Home gets ACLs + account split + telemetry, and that is what the leading OSS ships — honestly.

Inline risk table — detection class → mitigation → residual risk (Home-feasible unless marked Pro):

| Detection class | Mitigation (Home baseline; Pro adds) | Residual risk |
|---|---|---|
| Admin child account | Install-time gate refuses completion + red Devices-page banner; agent reports `admin_revoked` as tamper (Pro: Assigned Access/AppLocker can block un-allowlisted exes) | **Total defeat possible** — admin can remove agent; ship tamper-evident alert only. Documented, not solved. |
| Safe mode boot | `BOOT_COUNT` via `HKLM\SYSTEM\Setup` non-volatile key + service-start gap detection; report `safe_mode_boot` | Enforcement absent in safe mode (Home cannot fix); Phase-5 Pro option: SafeBoot-register service (consciously, rarely worth it). vigil claims safe-mode operation — treat as unverified. |

| Other OS (USB/dual-boot) | None — same class | **Total bypass**; documented, not solved. |
| Browser policy overwrite | HKLM keys require admin; HKCU keys child-scoped; on-device `edge://policy` self-check reported to parent | Admin child clears keys — Pro's AppLocker/SRP recovers some ground; otherwise alert-only. |

Unsolvable in-pixel, by design. |
| Safe-search "configured but hollow" | `ForceBingSafeSearch=2`, `ForceGoogleSafeSearch=true`, `ForceYouTubeRestrict` — the 0/false/Moderate traps documented ([Edge policy](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/forcebingsafesearch)) | Bing region-lock message can persist regardless of local keys — cosmetic, not a hole. |
| ISP/DHCP DNS hijack or fallback | Static per-adapter DNS → 127.0.0.1; **no secondary resolver**; IPv6 RA disabled or pinned | DHCP re-supply on renew is mitigated by static config; router-level beats ISP, fine later. |
| TOTP/offline unlock brute force | PBKDF2, 5 fails → 10-minute wait, mac-style offline codes, report `offline_unlock` | An admin child reads cached codes — acknowledged in vigil's threat model; alert-only. |
| Family desktop PC used for school (browser needed) | Browser never app-blocked; only DNS/policy filtered; Teams/Discord default allowlist | Precedent set: chat tools stay reachable — intended. |

The pattern to copy for honesty is Qustodio's "tampering detected" notice ([Qustodio help](https://help.qustodio.com/hc/en-us/articles/)) — but with a **continuous re-check loop**, not reactive alerting, and local fail-closed enforcement so a Dec-2025-style cloud outage degrades to "still works," never to "silently gone."

## Conclusion

The research changes the plan's center of gravity in one sentence: the Family Safety failure catalog proves that account-bound, cloud-synced controls collapse silently, and the OSS field proves the only control that holds is a session you end — so `jarvis-guard` should be engineered, messaged, and reviewed as "a signed, honest sheriff for the session," with the overlay, tray shield, web filter, and attestation chain all in service of that one enforcement point. The parent-developer's structural advantages — owning the machines, installing elevated, shipping signed provenance, and refusing stealth — are worth more than any technique the suites deploy; the two decisions that most determine success are (1) committing to logoff-as-enforcement on **Home as the baseline** rather than an overlay that always loses, and (2) pinning DoH off everywhere before enabling a single category list. Everything else — net10, Artifact Signing, the risk table, the MIT harvest — is execution. The residual holes (admin child, safe mode, USB boot) are not defects of this design; they are the price of Windows not being ChromeOS, and the plan should say exactly that on the Devices page and in the parent-facing guide, because a parent who understands the boundary enforces it in the household, which no agent can do for them.
