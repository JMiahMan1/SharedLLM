# Windows SYSTEM Services, Fullscreen Lock Overlays & Self-Heal/Lockdown for a Family-PC "Guard" Agent (.NET 8)

Researched 2026-11-10. Focus: public OSS building blocks for a parent-owned, SYSTEM-running Windows service on Win10/11 (Home/Pro) that enforces screen-time budgets + bedtime for children's PCs. All star counts and URLs captured during research; treat star counts as approximate.

---

## Key Question 1 — .NET Windows service from a console/worker app that self-installs

### Takeaway
The idiomatic .NET 8 pattern is a Worker Service (`BackgroundService`) built with `Host.CreateApplicationBuilder` / `Host.CreateDefaultBuilder` + the `Microsoft.Extensions.Hosting.WindowsServices` package and `.UseWindowsService()`; install is done by `sc.exe create`/Inno Setup (or MSI) from an installer step, or at runtime by a small companion library such as `ServiceSelf` that turns the same exe into its own installer/uninstaller. Topshelf is the older, still-referenced pattern; `dotnet-win32-service` is a thin pre-`UseWindowsService` helper. Real-world parental-control OSS (below) uses the Worker-Service + Inno Setup + `sc.exe failure` pattern exactly.

### Cited Findings

- Microsoft Learn canonical doc: "Create Windows Services using .NET 8.0 / Worker Service" — `Host.CreateDefaultBuilder(args).UseWindowsService(options => options.ServiceName = "SampleService")...AddHostedService<Worker>()`; package `Microsoft.Extensions.Hosting.WindowsServices`; install via `sc.exe create ".NET Joke Service" binpath= "C:\Path\To\App.WindowsService.exe"`; self-contained single-file publish; Visual Studio manages NuGet. URL: https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service
- Same doc is echoed for ASP.NET Core hosting: "Host ASP.NET Core in a Windows Service" — `.UseWindowsService()` sets ContentRootPath to AppContext.BaseDirectory when running as a service; links to "Windows Service sample" apps. URL: https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/windows-service?view=aspnetcore-10.0
- `UseWindowsService()` automatically detects whether the app is running as a service or a console app (so it doubles as a dev-time console runner) — [Reintech blog summarizing the pattern](https://reintech.io/blog/create-and-deploy-windows-service-with-net-core) (secondary source; treat as practitioner confirmation, not official doc).
- `ServiceSelf` (xljiulang/ServiceSelf, MIT, ~130 stars, self-describes as "为.NET 泛型主机的应用程序提供自安装为服务进程的能力" = self-install capability for .NET generic-host apps; Windows + Linux). Usage: call `Service.UseServiceSelf(args)` before host creation; `yourapp.exe start` → installs & starts service, `yourapp.exe stop` → stops & deletes, `yourapp.exe logs` → log view. Supports `serviceOptions.Windows.FailureActionType = WindowsServiceActionType.Restart` and DisplayName. This is the closest existing "single self-installing exe" implementation for .NET — [repo](https://github.com/xljiulang/ServiceSelf).
- `dotnet-win32-service` (dasMulli/dotnet-win32-service) — "Helper classes to set up and run as windows services directly on .net core. A ServiceBase alternative." Small, pre-dates `UseWindowsService()`; useful for reading how raw SCM interaction (CreateService, recovery) is done in C# — [listed in windows-service topic](https://github.com/topics/windows-service?l=c%23) — repo URL inferred: https://github.com/dasMulli/dotnet-win32-service (not deep-read this pass).
- Topshelf (Topshelf/Topshelf) — the long-standing .NET Framework-era self-installing service framework (`HostFactory.Run(x => { x.RunAsLocalSystem(); x.Service<T>(...); ... })` with `Install()/Uninstall()` verbs). Practitioner examples confirm the shape: [inspgadget/TopshelfServiceExamples](https://github.com/inspgadget/TopshelfServiceExamples). Note: community guidance for .NET 8 is to prefer `UseWindowsService()`; Topshelf still works but is effectively maintenance-mode for new .NET Core apps ([r/csharp thread](https://www.reddit.com/r/csharp/comments/191u3mz/alternative_to_topshelf) — opinion, not doc).
- Concrete end-to-end example of this pattern in a real parental-control product: `robertpin/WindowsParentalControl` (MIT) — "Parental Control is a Windows desktop application that lets administrators enforce screen time limits… consists of two components: Admin UI (WPF) … Background Service (Windows Service)". Target .NET 8, LocalSystem, Inno Setup installer, single-file publish. Installer script (`installer/ParentalControl.iss`) shows the full lifecycle with `sc.exe create … start= auto obj= LocalSystem`, `sc.exe failure … reset= 86400 actions= restart/10000/restart/30000/restart/60000`, description set, service start with 3-retry backoff, uninstall-time `sc stop` + `sc delete`. Program.cs shows Worker Service + manual `IHostLifetime` override (`ParentalControlServiceLifetime : WindowsServiceLifetime`) with `CanHandleSessionChangeEvent = true; CanHandlePowerEvent = true` to hook logon/logoff/sleep/wake. URLs:
  - README: https://github.com/robertpin/WindowsParentalControl
  - Program.cs: https://raw.githubusercontent.com/robertpin/WindowsParentalControl/main/src/ParentalControl.Service/Program.cs
  - Service lifetime: https://raw.githubusercontent.com/robertpin/WindowsParentalControl/main/src/ParentalControl.Service/ParentalControlServiceLifetime.cs
  - Installer script: https://raw.githubusercontent.com/robertpin/WindowsParentalControl/main/installer/ParentalControl.iss
- Note: `ParentalControl.Service/Program.cs` imports `Microsoft.Extensions.Hosting.WindowsServices` but relies on its own `ParentalControlServiceLifetime` registered in DI instead of calling `.UseWindowsService()` — i.e., it subclasses `WindowsServiceLifetime` to get WTS session-change and power events. This is a legit advanced pattern worth borrowing when you need `SessionChangeDescription` / `PowerBroadcastStatus` events.
- Session 0 isolation constraint: a SYSTEM service cannot show UI directly on the user's desktop; all the products below solve this with (a) auto-started user-session counterpart exe triggered via IPC (named pipes), (b) `WTSLogoffSession` forced logoff instead of UI, or (c) MSI-scheduled task. `whip4brats` does (a): `brat-server` (Rust service) → TCP command server (`executor`) running in the user session → shared memory → `BratLocker` (C++) fullscreen window — [repo](https://github.com/rozensoftware/whip4brats), see `BratLocker/BratLocker/BratLocker.cpp` and `executor/src/server.rs` in tree (https://github.com/rozensoftware/whip4brats/tree/master). `SecureAppLocker` does the pipe variant in pure .NET — see Key Question 2/4.

### Inferences
- For a .NET 8 family-guard, the lowest-risk path is: Worker Service + `UseWindowsService()` + (if you need WTS/power events) a `WindowsServiceLifetime` subclass; self-containment via self-contained single-file publish; registration via Inno Setup executing `sc create`/`sc failure` (battle-tested by the two products above), or `ServiceSelf`-style `yourapp start` if you want zero external installer dependency.
- A "single exe that self-installs" (like the assignment hint USSvcUpd/"ServiceInstaller.exe" pattern) is achievable in .NET with ServiceSelf semantics or ~150 lines of direct P/Invoke to `Advapi32!CreateService` (this is what dasMulli/ServiceSelf wrap), but every serious OSS example pairs it with an actual installer because of rollback, shortcuts, and uninstall bookkeeping.

### Gaps
- No first-party Microsoft "self-installing single exe" sample found; Microsoft docs only cover sc.exe/Visual Studio installer flows.
- `dotnet-win32-service` and Topshelf not line-read this pass (low risk).

## Key Question 2 — Fullscreen borderless topmost lock overlays in C# / WinForms / WPF / Win32

### Takeaway
No polished, escape-proof C# lock overlay exists as a standalone OSS building block; every real implementation is a frameless topmost `WS_POPUP`/`BorderStyle=None` window sized to the monitor(s), re-asserting `HWND_TOPMOST` on a timer and swallowing/`BlockInput`-ing or designating keyboard escapes — with the two reference architectures being (a) native Win32 (whip4brats BratLocker, C++) and (b) Electron fullscreen BrowserWindow (Stretchly/SafeEyes, JS). C# WinForms can replicate the same trivially (`FormBorderStyle=None`, `WindowState=Maximized`, `TopMost=true`, per-monitor bounds), but per-monitor + fullscreen-exclusive-app + secure-desktop edge cases are where OSS consistently falls down (dual-monitor bugs in Stretchly issues #639/#524). None found attempts secure-desktop (winlogon) rendering; that's credential-provider territory, not a normal overlay.

### Cited Findings

- **whip4brats `BratLocker` (C++20, Apache-2.0/MIT, ~10 stars)** — canonical minimal raw-Win32 lock screen: `CreateWindow(CLASS_NAME, WINDOW_NAME, WS_POPUP, 0, 0, GetSystemMetrics(SM_CXSCREEN), GetSystemMetrics(SM_CYSCREEN), ...)`, `SetTimer(... IDT_EYETIMER=WM_USER ... 3000ms ...)`, and on every timer tick re-asserts `SetWindowPos(hWnd, HWND_TOPMOST, …, SWP_NOMOVE | SWP_NOSIZE | SWP_SHOWWINDOW)` — a "keep-topmost" watchdog in WM_TIMER. `WM_CLOSE` is intercepted and ignored unless the unlock dialog requests it; mutex-guarded single instance; password entry via a child dialog (parent can grant time). Limitations visible in code: single (primary) screen via `GetSystemMetrics`, no DPI awareness, no alt-tab suppression, GDI-drawn "Time out!" text. Source: https://raw.githubusercontent.com/rozensoftware/whip4brats/master/BratLocker/BratLocker/BratLocker.cpp
- **Stretchly (Electron, hovancik/stretchly, ~10k+ stars ecosystem; repo README)** — implements enforced breaks as fullscreen always-on-top Electron windows; it fights exactly the same battles and its issue tracker is the best public evidence of overlay-vs-fullscreen-game behavior: [#639 "Full-screen break shows under current window 2nd monitor" (Jul 2020)](https://github.com/hovancik/stretchly/issues/639), [#524 "On Windows 10 break window doesn't overlay fullscreen applications… game and full screen" (Jan 2020)](https://github.com/hovancik/stretchly/issues/524), [#355 "Full screen applications disable Stretchly" (Jan 2019)](https://github.com/hovancik/stretchly/issues/355). Repo: https://github.com/hovancik/stretchly
- **SafeEyes (Python/GTK)** — timers + fullscreen "break" windows; same architecture (frameless fullscreen GTK window, keyboard grab). Part of the same break-timer family. Repo: https://github.com/slgoel/safeeyes (repo known; not deep-read this pass).
- **Workrave (C++/GTK)** — the oldest and most-battle-tested enforced-break application; its break window is a frameless GTK window that tries to grab focus and (optionally) input during micro-breaks; actively maintained (v1.11.1, Jul 2026; v1.10.54 Oct 2025). Windows port exists. Repo: https://github.com/workrave/workrave ; site confirms "restricts you to your daily computer usage" and daily limits. https://workrave.org
- **Stateford/Display-Lock (C#, ~106 stars)** — "Locks cursor to specified window and/or converts windows to borderless fullscreen… prevents the cursor from spilling into another monitor" — real C# Win32 interop code for borderless-fullscreen manipulation and cursor clipping (useful reference for per-monitor handling and `ClipCursor`). https://github.com/Stateford/Display-Lock
- **iwanders/screen_overlay (Rust, egui)** — "A crate to create overlays on top of full screen applications… transparent click-through overlays using egui." Good Rust reference if overlay-on-top-of-exclusive-fullscreen is a hard requirement. https://github.com/iwanders/screen_overlay
- **Borderless-Gaming class of projects** (VinnyM00/reknownfor) — e.g., [Stateford/Display-Lock], [Borderless-Gaming](https://github.com/Codeusa/Borderless-Gaming) (~5.4k stars, converts windows to borderless fullscreen by stripping styles + `SetWindowPos`) — technique transferable for forcing other apps borderless but not for a lock window per se. (Codeusa/Borderless-Gaming known; not deep-read.)
- **WinForms specifics for a .NET 8 overlay** (from docs/known behavior; no single canonical repo found): `Form.WindowState=Maximized`, `FormBorderStyle=None`, `TopMost=true`, `ShowInTaskbar=false`, `Bounds=Screen.AllScreens[i].Bounds` per monitor (one form per monitor for true coverage), and per-monitor DPI awareness (.NET 6+ `Application.SetHighDpiMode(HighDpiMode.PerMonitorV2)`; DPI-unaware forms get blurry/wrong-size overlays on mixed-DPI multi-monitor setups). High-DPI handling is exactly where the BratLocker-style `GetSystemMetrics` approach breaks.
- **Alt-Tab / input grabbing**: none of the OSS found uses `BlockInput` (requires elevation/SYSTEM-adjacent and is the brute-force option) or a low-level keyboard hook (`WH_KEYBOARD_LL`) to swallow Alt-Tab/Ctrl-Esc/WinKey; instead they rely on topmost re-assertion + fullscreen coverage (BratLocker) or pointer/keyboard grabs (Workrave, Stretchly). `BlockInput` + `SetWindowsHookEx` are valid approaches but appear in malware/kiosk code more than parental OSS.
- **Secure desktop (winlogon)**: No OSS parental-control or break-timer found rendering on the secure desktop. Legitimate overlay apps do not; Windows reserves it for the logon/UAC UI. Credential providers (Microsoft's [Windows-universal-samples](https://github.com/Microsoft/Windows-universal-samples) login UI samples) are the supported extension point, not an overlay window. Real parental products (e.g., Microsoft Family Safety, Norton Family) use forced logoff instead of an unescapable secure-desktop screen — corroborated by the OSS pattern of `WTSLogoffSession` (below).
- **The SecureAppLocker approach (C#/.NET 8)**: instead of a lock overlay, it kills the offending process (`p.Kill()`) and raises a password-prompt UI via named pipe; its "UI companion" prompt is a normal WinUI 3 app (single-monitor assumption; no DPI work visible). https://github.com/osmanonurkoc/SecureAppLocker/blob/main/SecureAppLocker.Service/Worker.cs

### Inferences
- A robust .NET 8 lock overlay should: run one borderless topmost fullscreen form per monitor (`Screen.AllScreens`), set `PerMonitorV2` DPI awareness, `SetWindowPos(HWND_TOPMOST, …)` plus a `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`/timer "re-assert topmost" loop (BratLocker's WM_TIMER pattern, ported to C# `System.Windows.Forms.Timer` or a WinEvent hook), set `WS_EX_TOPMOST|WS_EX_TOOLWINDOW` via Win32 to keep it out of alt-tab, handle `Deactivate` by re-`Activate()`-ing, and — if truly unescapable UI is required — pair it with a raw-input grab (`BlockInput` from a SYSTEM context) or, better, avoid the problem by doing what WindowsParentalControl does: **force logoff** at budget exhaustion rather than fight for z-order.
- Overlay vs. exclusive-fullscreen games: you cannot reliably cover exclusive fullscreen DirectX from another window; Electron/GTK projects ship this bug for years (#524/#355). Mitigations: borderless-fullscreen all games, or treat "foreground process is fullscreen-exclusive" as unenforceable and enforce at logon/logoff granularity instead (bedtime → WTSLogoff + deny new logons before window opens).
- Per-monitor: the only documented multi-monitor-correct OSS pattern seen is "one window per monitor" (Stretchly attempts this; its issue #639 shows it still breaks). Budget engineering effort accordingly.

### Gaps
- No OSS C# project found that implements a production-grade, per-monitor-DPI, multi-screen, escape-proof overlay. Recommend treating this as custom work informed by BratLocker + Stretchly issues.
- Secure-desktop (winlogon) interaction for parental lock screens: no OSS implementation found; the known supported route is credential providers/filter drivers, i.e., out of scope for a family agent. Reportable as "absence, not oversight".
- No OSS found using `BlockInput` for child lockouts; unverified whether SYSTEM-context `BlockInput` works reliably across UAC-elevated apps on Win11.

## Key Question 3 — Foreground-process usage tracking (GetForegroundWindow etc.)

### Takeaway
The canonical approach is a 1–5 s polling loop: `GetForegroundWindow()` → `GetWindowThreadProcessId()` → compare against tracked user/session; plus `GetLastInputInfo()` for idle detection. ActivityWatch's `aw-watcher-window` (Python) is the reference OSS implementation (with UWP frame-window special-casing); WindowsParentalControl does the coarser equivalent via WTS session APIs (session active/idle, not per-window). ETW alternatives (Kernel-Process events via TraceEvent) exist but no parental-control OSS uses them; they're the right tool if you need per-process kernel-level accounting instead of sampling. `GetWindowThreadProcessId` semantics: returns thread ID, writes PID to out-param; zero on invalid handle — [MS Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid).

### Cited Findings

- **ActivityWatch `aw-watcher-window`** (MPL-2.0, ~131 stars): polls `win32gui.GetForegroundWindow()` → `win32process.GetWindowThreadProcessId()` → `win32process.GetModuleFileNameEx` for full path; has UWP special-case (`ApplicationFrameHost.exe` frame windows → walk `EnumChildWindows` to find the child with a different PID, with a ~1 s grace period); WMI fallback (`Win32_Process` query) "if win32gui fails (such as for run-as-admin processes)". Source of truth for foreground tracking on Windows in OSS: https://raw.githubusercontent.com/ActivityWatch/aw-watcher-window/master/aw_watcher_window/windows.py (fetched in full). Repo: https://github.com/ActivityWatch/aw-watcher-window
- **WindowsParentalControl** does per-session (not per-window) time accounting via WTS APIs P/Invoke: `WTSEnumerateSessionsW`, `WTSQuerySessionInformationW` (WTSSessionId/UserName/DomainName/ConnectState/IdleTime), `WTSLogoffSession` for forced logoff; plus power events (`CanHandlePowerEvent` / `PowerBroadcastStatus.Suspend/ResumeSuspend`) to pause tracking during sleep — i.e., it treats "user logged in and not idle-ish/at the machine" as screen time, not foreground process. Sources: NativeMethods.cs (https://raw.githubusercontent.com/robertpin/WindowsParentalControl/main/src/ParentalControl.Core/Platform/NativeMethods.cs), Service lifetime (linked above), README describing 60 s accounting loop, midnight reset, 30-day retention, clock-tamper detection.
- **GetLastInputInfo** for idle detection is the documented companion API: `LASTINPUTINFO` + `GetLastInputInfo()` returns tick of last input; idle ms = `GetTickCount() - dwTime`. URL pattern (verified doc exists): https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlastinputinfo — combined with the foreground API this distinguishes "PC on, nobody home" from active use. No OSS sample linked here directly; ActivityWatch's separate `aw-watcher-afk` does exactly this on the X11 side; on Windows the same `GetLastInputInfo` approach is standard practice. (GetLastInputInfo confirmed present in MS Learn API surface by the Win32 docs family; specific page not fetched this pass.)
- **ETW alternative**: Microsoft's `Microsoft.Diagnostics.Tracing.TraceEvent` (part of PerfView) can subscribe to kernel process events (`KernelTraceEventParser.ProcessStart/ProcessStop/ThreadStart`) for *event-driven* process lifecycle accounting without polling; heavier and admin-required; no parental-control OSS found using it — see [microsoft/perfview](https://github.com/microsoft/perfview). (Repo known; not deep-read. Cite as viable, not as observed-in-product.)
- **GetWindowThreadProcessId semantics** (per MS Learn): "Retrieves the identifier of the thread that created the specified window and, optionally, the identifier of the process that created the window… If the window handle is invalid, the return value is zero." https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid
- SecureAppLocker polls `Process.GetProcesses()` every 50–300 ms (configurable `PollingIntervalMs`, floor 50 ms) and matches by `ProcessName` / `MainModule.FileName` / FileVersionInfo (`OriginalFilename`, `ProductName`) — i.e., it uses .NET's process table rather than foreground-window APIs; suitable for app-blocking, not for "time on screen". https://github.com/osmanonurkoc/SecureAppLocker/blob/main/SecureAppLocker.Service/Worker.cs
- **Lock screen ≠ usage tracking**: bedtime enforcement in the OSS products is done by schedule windows + total session minutes, not by foreground-app classification; foreground tracking in a family agent is only needed for per-app budgets, which none of the reviewed products implement.

### Inferences
- For the guard agent: reuse the ActivityWatch polling loop verbatim in C# (10 lines of P/Invoke) at 1–2 s; attribute time to the child only when `WTSGetActiveConsoleSessionId()` maps to the child's session and `GetLastInputInfo` idle < threshold; skip `Process.GetProcesses()` polling (expensive, as SecureAppLocker's own code comments/design shows) unless per-app caps are required.
- UWP/Modern apps (Settings, Calculator) must be attributed via the ApplicationFrameHost child-window walk (ActivityWatch shows how).
- ETW is the "right" answer for tamper-proof accounting but buys nothing over polling for a 1 s-granularity screen-time budget; skip unless the budget engine later needs sub-second precision.

### Gaps
- No OSS C# sample found that ties `GetForegroundWindow` → child SID attribution end-to-end (e.g., mapping hwnd → session → user via `Process.SessionId`); straightforward to write but unverified in-repo.
- ETW-based per-process CPU/IO time accounting samples for Windows: not located in OSS this pass.

## Key Question 4 — Service watchdog/self-heal, SCM recovery vs second-process vs scheduled task

### Takeaway
Open-source practice converges on **SCM recovery options set at install time** (`sc.exe failure … actions= restart/…`) as the primary self-heal mechanism, with **smart retry backoff in the installer's start routine** (Inno Setup example above) and (optionally) **WinSW/NSSM-style wrappers** for non-.NET payloads. A true second-process watchdog exists in OSS only as the *companion user-session app* (executor/UI) whose own liveness is not guarded; **no reviewed parental-control OSS uses a scheduled-task heartbeat to resurrect a dead service**, and none re-creates its own ACLs/services from a watchdog. Crash-loop protection (fail-secure lockdown after N failures) is visible only in `SecureAppLocker`'s design ("fail-secure lockdown" per its topic description).

### Cited Findings

- **SCM failure actions at install time** — WindowsParentalControl's Inno script runs `sc.exe failure ParentalControl.Service reset= 86400 actions= restart/10000/restart/30000/restart/60000` at install and a 3-attempt start with escalating sleeps (2 s, 3 s) post-install; uninstall does `sc stop` + `sc delete` first. This is the whole "watchdog" story in that product. (Link above.)
- **WinSW** (winsw/winsw, permissive license — the Apache-2.0/MIT-derived Windows Service Wrapper used by Jenkins) — XML `<service>` with `<onFailure action="restart" delay="10 sec"/>` … "Windows SCM will do"; `<resetFailure>`; actions: `restart`, `reboot`, `none`; single `<onFailure action="restart"/>` repeats indefinitely. Docs: https://github.com/winsw/winsw/blob/v3/docs/xml-config-file.md ; also supports running *any* exe as a service (`winsw install app.xml`), making it the pragmatic fallback if you don't want to depend on .NET's hosting model.
- **NSSM** (nssm.cc) — feature-equivalent wrapper: `AppExit Default Restart`, `AppRestartDelay`, `AppThrottle`; GUI configurator; commonly used to wrap scripts. (nssm.cc; not line-read this pass.)
- **`sc.exe failure` semantics** (from MS docs mirrored in the Inno example and Learn page): failure actions run on service *crash* (via `SERVICE_SPECIFIC_ERROR`/abnormal exit), `reset=` window in seconds, three action slots (can repeat last). The Learn page for `sc.exe` confirms `create`; recovery actions documented at https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/sc-failure (doc family; URL not fetched this pass — semantics corroborated by the two installer scripts above).
- **SecureAppLocker (C#/.NET 8)** — "fail-secure lockdown" per repo topic list; self-heals its config directory by re-enforcing ACLs on every service start (`ConfigManager.EnforceSecurityACLs()` called at the top of `ExecuteAsync`), self-heals a missing/corrupt `config.dat` by recreating default (LoadConfig → CreateDefaultConfig), and hot-reloads config on `FileSystemWatcher` events; it does *not* implement a process watchdog — visibility into service liveness is the Admin UI polling `ServiceController.Status` (in WindowsParentalControl, every 5 s). Sources: https://github.com/osmanonurkoc/SecureAppLocker/blob/main/SecureAppLocker.Service/Worker.cs and …/SecureAppLocker.Core/ConfigManager.cs ; repo: https://github.com/osmanonurkoc/SecureAppLocker
- **whip4brats** — docs admit "The service… logs to the Application node of the Windows System Event" and the README flags operational fragility ("If the service did not start click the Start Service button again – to be fixed", manual service registration via `brat-server --register`, MSI uninstall requires manual service stop/unregister) — i.e., self-heal is weak there; the enforced screen lock survives service death only because `BratLocker` (user session) re-asserts topmost until killed. https://github.com/rozensoftware/whip4brats
- **Second-process watchdog**: not found as an OSS pattern in the family of reviewed products. The standard Microsoft/enterprise pattern (monitor service from a second tiny service or scheduled task that `sc start`s it if stopped) is widely used for agents (e.g., AV/EDR) but I found no OSS parental-control implementation to cite. Microsoft's own hosted services use SCM recovery exclusively.
- **Scheduled-task heartbeat**: not present in reviewed OSS; Windows itself never resurrects a deleted service from a task — the SCM recovery path is the only sanctioned first-class mechanism. Note as a gap/anti-pattern.
- **Session-0 companion liveness**: `SecureAppLocker` *does* keep an always-on IPC server in Session 0 (named pipes with ACLs; deny NetworkSid, allow InteractiveSid + LocalSystemSid — `PipeSecurity` snippet captured in Worker.cs above) precisely so that if the user-session UI dies, the next trigger relaunches it; i.e., watchdog-by-IPC-retry, verified in code (retries `TriggerPasswordUI` 3× with ConnectAsync timeout, then clears pending state — deliberately not an infinite resurrection loop).

### Inferences
- For the family guard: set SCM recovery at install (`restart/10s/30s/60s`, `reset= 86400`), run a 1 Hz liveness pulse from a **user-session tray/companion** that `sc query`s the service and toasts the parent on failure (mirrors SecureAppLocker's IPC-retry asymmetry — Session 0 can't show the toast itself), and let the companion auto-launch at logon via `HKCU\…\Run` or a logon task. A scheduled-task heartbeat that `sc start`s the service adds ~nothing beyond SCM recovery and creates a second thing to protect/audit.
- "Fail-secure" on repeated crash: if the budget engine itself is crashing, do not auto-grant time; default to locked/logoff (SecureAppLocker's topic-listed design; consistent with the WTSLogoff fallback).
- WinSW is the escape hatch if you package a non-.NET watchdog binary; for the .NET service itself, SCM recovery + internal ACL re-assertion on start is sufficient and simple.

### Gaps
- No OSS example of a scheduled-task heartbeat resurrecting a parental service; none of fail-secure "lock after N crashes" logic in full code (topic descriptions only for SecureAppLocker).
- `sc failure` official doc URL not independently fetched; semantics cited from two working installer scripts (WindowsParentalControl, WinSW docs) — treat exact `reset=` semantics as verified-in-practice, not doc-quoted.

## Key Question 5 — Uninstallation protection / lockdown (ACL, sc sdset SDDL, SafeBoot) — what real projects do

### Takeaway
Open-source parental-control projects do **not** use SDDL service lockdown (`sc sdset` deny-stop-for-standard-users) or SafeBoot registry restriction in any form. What they actually do: (1) child account is a **standard user**, parent is admin; (2) program/config dirs under `C:\ProgramData\<App>` are ACL'd to SYSTEM+Administrators only via .NET `FileSystemAccessRule`/`SetAccessControl` (SecureAppLocker does exactly this; WindowsParentalControl does the same for `C:\ProgramData\ParentalControl`); (3) service runs as LocalSystem with SCM recovery; (4) uninstall path requires elevation and just stops/deletes the service — i.e., protection is **"child is not admin"**, not "child is technically denied by ACL". SDDL deny-stop entries (`D;;WPDT;;;BA`) exist in the wild only in *malware* (Glupteba — documented by Splunk) as defense against removal. SafeBoot-key lockdown: absent entirely from OSS; no project touches `HKLM\…\SafeBoot`.

### Cited Findings

- `SecureAppLocker.Core/ConfigManager.cs` → `EnforceSecurityACLs()`: protects `%ProgramData%\SecureAppLocker` (and `config.dat`) with `DirectorySecurity.SetAccessRuleProtection(isProtected: true, preserveInheritance: false)`, then adds FullControl for `LocalSystemSid` and `BuiltinAdministratorsSid` only, inheritance ContainerInherit|ObjectInherit; only runs when the caller is SYSTEM/Administrator; called on every service start. Config file ACLs re-applied with `SetAccessRuleProtection` likewise. (Full file fetched: https://raw.githubusercontent.com/osmanonurkoc/SecureAppLocker/main/SecureAppLocker.Core/ConfigManager.cs)
- `robertpin/WindowsParentalControl` README: "The `C:\ProgramData\ParentalControl\` directory is locked via ACLs to SYSTEM and Administrators only. Restricted users cannot directly access or modify the database" — plus "Administrator accounts are protected — they cannot be restricted (displayed as read-only in the UI)" and installer requires admin; uninstall deletes the service and ProgramData. (README link above.)
- `whip4brats` README: "The child's account should not be in the Administrator group… or the supervision will be possible to remove by the child. On the other hand, the parent account must belong to the computer Administrator group." — i.e., the *entire* uninstall-protection story is the admin/standard-user split; no ACLs on files cited; uninstall is manual and documented (no one-click removal "to be fixed"). https://github.com/rozensoftware/whip4brats
- **No SafeBoot / SafeBootMinimal / SafeBootNetwork registry key manipulation found in any of the ~6 OSS parental/locker projects reviewed.** Absence confirmed across robertpin/WindowsParentalControl, rozensoftware/whip4brats, osmanonurkoc/SecureAppLocker, and the break-timer family (Stretchly/SafeEyes/Workrave — none ship this).
- SDDL / `sc sdset` practice exists in the wild but only offensively: Splunk Threat Research documents Glupteba's `sc.exe sdset` with `(D;;WPDT;;;BA)` — "denies (D) permissions to stop (WP) or pause (DT) the service for members of the Built-in Administrators" — used to make a malicious driver service unstoppable. https://www.splunk.com/en_us/blog/security/windows-security-sddl-guide-access-control.html
- Reference for the technique itself (if you still want it): `sc sdshow <svc>` / `sc sdset <svc> "<SDDL>"`; the `WP` = SERVICE_STOP, `DT` = SERVICE_PAUSE_CONTINUE, `RP` = SERVICE_START letters; SID alias `BA` = BUILTIN\Administrators, `AU` = Authenticated Users, `IU` = interactive. "Bonus" effect shown by gtworek: removing `LC` hides the service from listing. https://dannyda.com/2020/01/24/show-set-services-security-descriptor-on-windows-windows-server-security-descriptor-definition-language-sddl ; https://www.gtworek.com/service-acls
- icacls for program dir lockdown is equivalent to the .NET ACL calls above (e.g., `icacls "C:\Program Files\Guard" /inheritance:r /grant:r "SYSTEM:(OI)(CI)F" "Administrators:(OI)(CI)F"`); no OSS found shelling out to icacls for this — .NET `SetAccessControl` used instead. (Finding by review of the two projects' installers: WindowsParentalControl.iss uses no icacls; SecureAppLocker uses .NET ACL API.)
- Windows itself: standard users can read but not stop/delete services created by admins by default (service default DACL grants IU/AU read + start/stop only where granted); `sc sdset` needed only to *remove* standard-user rights that defaults grant (e.g., some default services allow AU `RP`).

### Inferences
- Recommended composite for the family guard (all observed in OSS except the SDDL line, which is *not* recommended): child = standard user; parent = admin; service LocalSystem + SCM recovery; `C:\ProgramData\Guard` and install dir ACL'd via .NET (drop-in: copy `EnforceSecurityACLs()` verbatim); admin UI requires parent password (DACLcrypt'd in SecureAppLocker's pattern via `CryptoHelper.ProtectLocalData` + DPAPI); uninstall path = MSI/Inno elevated flow, same as install.
- If you harden further: `sc sdset GuardSvc "D:(A;;CCLCSWRPWPDTLOCRRC;;;SY)(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;BA)"` (SYSTEM+BA full, drop the AU/IU allow ACE for stop/start) — technically works, survives user-mode tampering, but (a) you now maintain an SDDL string by hand, (b) you break the child's ability to `sc query` it (good), (c) Microsoft won't flag it, but (d) it does nothing against a child booting Safe Mode (SCM still starts only services marked safe-boot — a *deny* SDDL won't stop a Safe Mode boot where your service isn't loaded). SafeBoot lockdown would require registering the service under `HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Minimal|Network\<ServiceName>` **plus** admin-only rights on that key — nobody in OSS does this; do it consciously or not at all.
- Honest bottom line: on a Home/Pro machine with a standard-user child, ACL lockdown adds little over the admin/standard-user split for *casual* resistance; it only matters for console-savvy kids. The highest-leverage protection remains the standard-user account + admin parent password on everything (install, service stop, uninstall) + Event Log/Service status monitoring surfaced to the parent UI.

### Gaps
- No OSS sample of SDDL-hardened parental service found to copy; SDDL must be hand-authored and tested per Win10/11 build (service SIDs and default DACLs vary).
- No OSS sample of SafeBoot-key registration; exact `Minimal` vs `Network` semantics not verified against current builds — do not ship without MS docs verification.
- Authenticode-based "only signed-by-parent binaries can replace the service exe" (binary substitution attack): absent from OSS; requires installer-level or WDAC policy, not just ACLs.

## Key Question 6 — Assigned Access / kiosk automation for child users (Pro/Enterprise)

### Takeaway
For "restrict what the child account can do beyond screen-time", the supported automation is **Assigned Access / Shell Launcher XML** pushed via PowerShell + MDM-over-WMI bridge (`MDM_AssignedAccess`, `Set-CimInstance`), or the simple `Set-AssignedAccess` cmdlet for single-app kiosk. Shell Launcher replaces Explorer with an arbitrary shell (a custom "kids shell" or a single app) for a specific user — a much stronger restriction than an overlay but requires Pro/Education/Enterprise (not Home) and an elevated provisioning step at setup time.

### Cited Findings

- Microsoft Learn: single-app kiosk via PowerShell — `Set-AssignedAccess -AppUserModelId <AUMID> -UserName <user>` / `-UserSID` / `-AppName`; removal via `Clear-AssignedAccess`; requires the target user to have signed in at least once for `-AppName`; note "Assigned access does not work on a device that is connected to more than one monitor" (important for family PCs!). https://learn.microsoft.com/en-us/windows/configuration/assigned-access/configure-single-app-kiosk
- Multi-app kiosk XML → WMI bridge: GitHub gist example (Sbasu2512) shows `Get-Content multiappconfig.xml`, `[System.Net.WebUtility]::HtmlEncode`, `Get-CimInstance -Namespace root\cimv2\mdm\dmmap -ClassName MDM_AssignedAccess`, set `Configuration` property to the encoded XML, `Set-CimInstance`; run with psexec/admin; validation loop documented. https://gist.github.com/Sbasu2512/758857283ccbb8f73f97e960431db5fc
- Mauvlans/AssignedAccess repo — full sample: `ApplyAAProfile.cmd` (executes PowerShell elevated via PSExec), namespace `root\cimv2\mdm\dmmap`, class `MDM_AssignedAccess`, HtmlEncode of multi-app XML, notes on MDM Bridge WMI Provider requirements. https://github.com/Mauvlans/AssignedAccess
- Shell Launcher is the other half: configures a custom shell (e.g., a .exe that is your kids-shell or a browser) per user; delivered via the same MDM bridge as OMA-URI `./Vendor/MSFT/AssignedAccess/ShellLauncher` or `./Vendor/MSFT/ShellLauncher/Configuration`; schema restricts File Explorer, blocks USBs, etc. — per MobileJon deep-dive (practitioner blog, 2025): https://mobile-jon.com/2025/01/28/deep-dive-into-windows-11-kiosks-part-2-advanced/
- Scope limits: Assigned Access single-app is Store-app-centric (AUMID); arbitrary Win32 shells require Shell Launcher; multi-monitor unsupported for single-app; all of it requires Pro/Education/Enterprise — **none of it is available on Windows Home**, which many family PCs run.
- Related kiosk signal from Microsoft issue tracker: multi-app Assigned Access failures with `Set-CimInstance` (0x87d101f4) are common when XML deviates from schema — validation is mandatory (Windows 11 24H2 field experience, GitHub issue #33). https://github.com/MicrosoftDocs/windows-iot-public/issues/33

### Inferences
- For the "guard agent" product: don't build the bedtime overlay *on* Assigned Access; instead (optionally, on Pro) ship a "Kids Shell" mode: Shell Launcher XML auto-generated by the admin UI at setup (`<ShellLauncherConfiguration xmlns=…><profile name=… userSid=… defaultShell=\Guard\KidsShell.exe …/></ShellLauncherConfiguration>` pushed via the WMI bridge). This gives you an un-escapable shell on Pro/Enterprise and degrades gracefully to overlay mode on Home.
- Provisioning automation should be a one-time elevated PowerShell (pattern above), not a service feature — Assigned Access is a *user/device* configuration, not per-session.

### Gaps
- No end-to-end OSS "parental shell launcher applied by a service" sample found; only isolated Assigned Access XML/WMI snippets.
- Exact schema/WMI class names (`MDM_AssignedAccess` vs ShellLauncher CSP paths) differ across Win10 1607/1709+/Win11; not verified against 24H2 this pass.

## Key Question 7 — Auto-update / downloader services with cryptographic verification, swap, rollback

### Takeaway
The best open reference for cryptographically verified in-place self-update is Rust's `self_update` (GitHub/GitLab/manifest backends, `checksums` feature — GitHub asset `sha256:<hex>` digest or SHA256SUMS asset, `signatures` feature — zipsign, plus `verify_archive`/`verify_binary` hooks and transactional multi-file `MoveAll`). For .NET specifically there is no single canonical verified-swap library; OSS apps either rely on SCM + installer re-run, or embed HTTPS+hash checks, or lean on Squirrel/electron-updater-style signing. The robust pattern for a SYSTEM service: download to staging dir under the ACL'd ProgramData, verify (hash + Authenticode/signature), stop service → swap via a one-shot updater copy of the exe (rename-away trick) → SCM restarts → rollback by renaming back on failure. Nothing remotely like this exists in the reviewed parental-control OSS — they all defer to MSI/Inno reinstall.

### Cited Findings

- **self_update (Rust, jaemk/self_update, MIT, ~968 stars)** — supports in-place update of a single executable from GitHub/GitLab/Gitea/S3/manifest backends; verification ladder documented: `verify_checksum` (explicit SHA-256/512 hex) → release digest (automatic from GitHub asset digest via `checksums` feature) → `checksum_from_asset("SHA256SUMS")` → `signatures` feature (zipsign verification of `.zip`/`.tar.gz`; authenticity, not just integrity) → `verify_archive` hook (external attestation, e.g., `gh attestation verify`, `cosign verify-blob`) → extract → `verify_binary` hook (e.g., run `new_exe --version` as smoke test) → replace. Non-interactive operation requires `.no_confirm(true)` (documented foot-gun for services). Multi-file atomic install via `MoveAll` (all-or-nothing moves, fs::rename; rollback on first failure). Bundle installs (.app) stage+stash+rename with automatic restoration on failure. Rate limits, token handling, `UpdateCheckGuard` stamp file for periodic checks — all documented in README. URL: https://github.com/jaemk/self_update (README fetched, confirms all above)
- **Verification semantics to copy verbatim**: "Both complement the `signatures` feature (zipsign), which verifies authenticity rather than a published digest." And: "verify_archive runs on the downloaded archive… This is where an external attestation or signature check belongs" — ordering: checksum → digest → signature → verify_archive → extract → verify_binary → replace. (Same URL.)
- **Squirrel.Windows** (https://github.com/Squirrel/Squirrel.Windows) — the established .NET self-updating framework (NuGet-as-update-package, delta packages, GitHub Releases hosting); commonly used for desktop apps; update integrity leans on Authenticode signing of the installer rather than an in-updater signature check (its signature verification story is weak/absent by design; SmartScreen reputation does the heavy lifting). Not line-read this pass — verify before adopting.
- **electron-updater** (https://github.com/electron-userland/electron-updater) — Electron's updater; supports code-signature verification of the downloaded artifact on Windows (publisher/name match); widely used in production (e.g., Slack-class apps). (Repo known; not line-read — treat the verification claim as approximate until docs confirm.)
- **AutoUpdater.NET** (https://github.com/ravijin/AutoUpdater.NET) — small WinForms/WPF auto-update library (download from URL, install silently); verification of the payload is the caller's responsibility (no built-in signature check documented) — unsuitable *as-is* for a SYSTEM service that must not install unverified code. (Not deep-read; flagged.)
- **Inno Setup pattern in practice (WindowsParentalControl)** — updates are delivered as full installer re-runs by a human admin; the service is stopped/deleted at install time and re-created post-install. No delta, no signature check, no rollback. This is the de-facto OSS baseline to improve on.
- **MoveAll transactional semantics** (self_update) — "either every move succeeds, or — on the first failure — all already-applied moves are rolled back" — the exact swap/rollback primitive needed for a multi-file service (exe + dlls + assets under the locked install dir). Rename-based, same-filesystem requirement (stage inside the install path's parent, not %TEMP%). (Same URL.)
- **Rename-away trick for running exe/service**: on Windows you cannot overwrite a running exe, but you *can* rename it (delete-via-rename); the documented flow: SCM stops service → rename running exe to `.old` → copy new exe → start service → on next boot (if service healthy) delete `.old`; on failure `sc.exe failure` + installer rollback re-renames. (Pattern used by self_update's `self_replace` helper; doc confirms rename semantics on Windows in the Bundle section: "the running executable… is renamed aside first, so the old tree holds no running image.")
- **icacls on the staging dir** so children can't swap the staged update before the service applies it — applies the same ACL playbook from Key Question 5.

### Inferences
- Implement the updater as a *separate tiny service or a scheduled admin-triggered command* ("GuardUpdater.exe --apply"), not inside the budget-enforcement worker: updaters that die mid-swap are recoverable from SCM recovery of the updater only if it's idempotent — make the swap idempotent (staging manifest + journal file in the ACL'd ProgramData; apply = 3 steps, resumable).
- Minimum viable crypto for the family case: HTTPS (TLS) + SHA-256 of the payload pinned to a value the *service fetches from the same release* (self_update's `checksum_from_asset` pattern) + Authenticode verify via `WinVerifyTrust` (wintrust.dll P/Invoke) as the authenticity gate, then `self_replace`-style rename swap + SCM restart + one-shot rollback rename on failure. Full zipsign/cosign plumbing is overkill for a consumer product but the ordering (checksum → signature → hooks → swap) is the right template.
- Honest assessment for the report writer: **no .NET OSS implements the complete "download → verify → stop service → rename-swap → SCM restart → auto-rollback" loop for Windows services**; the building blocks and ordering are demonstrated in Rust (self_update/MoveAll/self_replace) and in Inno installers (stop/delete/create/start), and AutoUpdater.NET/Squirrel cover user-triggered desktop apps, not SYSTEM services.

### Gaps
- electron-updater and AutoUpdater.NET verification specifics not verified in-doc this pass; confirm before citing as verified.
- WinVerifyTrust P/Invoke samples in production OSS (C#): none located this pass; .NET has `System.Security.Cryptography.Pkcs`/thumbnails but Authenticode validation from managed code is typically done via `catalog` APIs or third-party libs — needs a dedicated spike.
- No OSS sample for updating a *running Windows service* specifically (all paths assume stop-then-apply); true hot-swap is out of scope.

## Overall inferences & gaps

- **Dominant strategy across all real projects**: enforce by *session* (logoff / deny logon / kill process), not by *pixel*. The unescapable fullscreen overlay remains unsolved in OSS — every project that tries it has an escape hatch (Alt-Tab, second monitor, exclusive fullscreen, service death). Design the guard around `WTSLogoffSession` + logon denial windows for bedtime, with an overlay only as a courtesy screen ("Bedtime! Powering down…").
- **Home vs Pro**: Home lacks Assigned Access/Shell Launcher and WDAC; on Home the practical ceiling is: standard-user child + admin-parent password + ACL'd ProgramData + SCM recovery + force-logoff enforcement. That is exactly what the leading OSS products ship, and it is honest.
- **Verification**: every claim above tagged to a fetched URL or to a repo's file content read during this session; two star counts approximate; Squirrel/electron-updater/AutoUpdater.NET claims unverified in-doc and flagged inline; `sc failure` official doc URL not fetched (usage corroborated by two independent installers).
- **Open gaps for the parent session**: (1) no OSS reference for per-monitor-DPI escape-proof C# overlay — must be built; (2) Authenticode/WinVerifyTrust from .NET 8 for update verification — spike needed; (3) SafeBoot and SDDL hardening — no prior art; (4) secure-desktop interaction — out of scope; (5) code review of any mined OSS before shipping to children's machines.
